# Miniapp

## 技术栈与目录

- 使用 UniApp、Vue 3、TypeScript、Pinia、Vite。
- 当前主要支持 H5 和微信小程序，开发时注意 UniApp 跨端差异。
- `src/pages/`：页面与页面级业务逻辑。
- `src/components/`：跨页面复用的业务组件。
- `src/api/`：按业务领域组织 API 方法和接口类型。
- `src/services/`：请求、认证会话等基础设施。
- `src/stores/`：Pinia 全局业务状态。
- `src/utils/`：存储、格式化、图片地址等公共工具。
- `src/types/`：跨模块公共类型。
- `src/static/`：静态资源。

## 核心原则

- 保持实现简单、职责清晰，优先复用已有页面、组件、Store、API 和工具，不创建重复能力或无关抽象。
- 修改前先阅读当前业务对应的页面、API、Store 和公共能力，保持已有业务行为一致。
- 不因新增一个页面或接口创建大量空目录、Composable、Service 或通用组件。
- 页面负责展示与交互；可跨页面共享的业务状态和操作放入对应 Pinia Store。
- 只有至少两个实际场景需要时才抽取公共组件或公共逻辑，避免为了“架构完整”提前抽象。

## API Contract

- Swagger/OpenAPI 是小程序接口的唯一 Contract；接口字段、请求参数和响应结构以当前小程序 Swagger 为准，不根据页面需要猜测字段。
- `src/api/` 按业务领域维护薄 API 封装，例如商品、购物车、会员、订单和售后。
- 页面不要直接调用 `uni.request`，统一通过 `src/services/request.ts` 和 `src/api/` 调用后端。
- 新增或修改后端接口时，应同步核对 Swagger 和对应 `src/api/` 类型与调用。
- 不为了临时通过编译伪造接口、假数据或重复定义一套与真实 API 不一致的模型。

## 请求与错误处理

- 普通业务请求使用 `src/services/request.ts` 提供的公共请求能力，不在页面重复实现 Base URL、Token、HTTP 状态码或认证失效处理。
- 公共请求层负责 Token 注入、HTTP 异常、业务错误和认证失效处理。
- 当前请求层在请求失败或 `code !== 1` 时会抛出错误，因此页面和 Store 可以使用 `try/catch/finally` 处理加载状态、用户反馈和业务恢复。
- 捕获错误时保留有意义的用户提示，不静默吞掉关键业务错误。
- 允许明确属于“静默刷新、预加载、次要数据同步”的请求失败后只记录日志，不影响主流程。
- 401、Token 失效和账号切换统一走现有认证清理流程，不在业务页面自行清 Token 或维护第二套登录状态。

## 状态管理

- Pinia 只保存真正需要跨页面共享或长期维护的业务状态。
- 页面局部输入、弹窗开关、临时筛选条件等优先保留在页面内部，不全部放入 Store。
- 会员认证、购物车、商城公共配置等已有全局状态继续使用现有 Store，不创建第二份状态源。
- 涉及登录、退出、切换账号、异步刷新时，必须避免旧请求覆盖新账号状态。
- 修改会员、购物车等状态时检查关联 Store 是否需要同步刷新或清理，避免跨账号数据污染。

## 登录与认证

- Token 和会员资料统一通过现有认证存储工具及 Member Store 管理。
- 不在页面直接读写独立 Token Key，不创建新的认证 Storage。
- 登录成功后同步内存状态与持久化状态。
- 退出登录和认证失效时统一清理会员、Token、购物车以及与当前登录用户有关的临时状态。
- App 启动时继续使用现有初始化和会员刷新流程，不在各页面重复执行全局初始化。
- 微信登录、手机号登录等不同登录方式最终必须进入同一套会员状态和认证生命周期。

## 页面与组件

- 页面优先使用 Vue 3 `<script setup lang="ts">`。
- 保持模板、状态和事件命名清晰，避免一个页面堆积大量无关业务逻辑。
- 页面明显复杂时，优先按真实业务区域拆组件，例如商品 SKU 选择、订单商品列表、地址卡片；不要单纯为了缩短文件而拆分。
- 公共组件通过 Props 和 Emits 明确数据边界，不直接依赖其他页面内部状态。
- 列表页面必须明确区分首次加载、加载更多、空数据、失败和没有更多数据等状态。

## UniApp 与跨端

- 优先使用 UniApp 官方跨端 API，不直接依赖仅 H5 可用的浏览器 API。
- 必须使用平台专属能力时，通过 UniApp 条件编译明确隔离，例如 `#ifdef H5`、`#ifdef MP-WEIXIN`。
- 新增能力时至少检查 H5 与微信小程序两端是否存在 API、生命周期、路由、Storage 或样式差异。
- 不为了修复某一平台直接破坏另一平台已有功能。

## 金额与订单数据

- API 中金额继续保持后端定义的十进制字符串语义，例如 `price: string`、`amount: string`。
- 金额计算禁止依赖 JavaScript 浮点数进行订单、支付、优惠或结算计算。
- 展示格式化与真实业务计算分开；需要计算时使用项目已有精确金额工具或转换为整数分后计算。
- 商品价格、库存、订单状态等以后端返回为准，不根据前端本地状态推断真实业务结果。
- 支付、下单、退款等关键操作必须防止重复提交，并以服务端最终结果为准。

## 样式与交互

- 保持商城前台移动端体验一致，优先保证信息层级、触摸区域、滚动体验和主要操作可达性。
- 页面样式优先复用项目已有视觉语言，不因为新增页面引入另一套独立设计体系。
- 使用 `rpx`、flex 等适合 UniApp 的布局方式，并检查常见手机宽度。
- 关键按钮需要明确 Loading / Disabled 状态，避免请求期间重复操作。
- 空状态、错误状态和未登录状态提供明确下一步操作，不留下无法理解的空白页面。

## 修改边界

- 只修改当前任务需要的代码，不顺带大规模重构无关页面。
- 修复 Bug 时优先修复根因，不通过硬编码、延时、重复请求或假数据掩盖问题。
- 已存在公共能力时优先复用；发现公共实现存在问题时修复公共层，而不是在多个页面分别打补丁。
- 不提交真实 Token、密码、Secret、生产接口密钥或私人配置。

## 验证

修改 `miniapp` 后根据任务至少执行：

```bash
cd miniapp

pnpm run type-check
pnpm run test
```

涉及 H5 时执行：

```bash
pnpm run build:h5
```

涉及微信小程序时执行：

```bash
pnpm run build:mp-weixin
```

同时在仓库根目录执行：

```bash
git diff --check
```

无法执行的构建、真机、微信开发者工具或外部接口验证必须明确记录原因。
