# 登录与权限

## 状态归属

- JWT、当前用户、角色和权限统一存放在 `admin-web/src/framework/store/` 的 Zustand store。
- 权限判断也由该目录提供，例如统一的 `hasPermission`；业务模块不维护第二份权限集合。
- 不再创建独立 `auth` 目录，也不在页面、菜单或组件中直接解析 JWT。
- HTTP 层从 store 获取 JWT；如果任务需要修改 Token 注入、401 或网络异常处理，再按主 Skill 读取 `http.md`。

## 登录与持久化

- 登录接口和当前用户接口以 Swagger Contract 为准。
- 未选择“记住登录”时，Token 使用后端默认有效期并保存在 `sessionStorage`。
- 选择“记住登录 30 天”时，请求携带 `remember: true`，后端签发 30 天 JWT，前端保存到 `localStorage`；前端不得伪造或延长已过期 JWT。
- 同时保存后端返回的 `expires_at`，恢复状态时先判断是否已失效。
- 登录成功后写入 JWT，再获取并写入当前用户、角色和权限。
- 每次 F5 或应用重新加载时，如 JWT 仍有效，调用 `/api/auth/me` 刷新 user、roles 和 permissions。
- 退出登录、401 或 Token 失效时统一清空 JWT、用户、角色、权限以及 `sessionStorage`、`localStorage` 中的相关内容。

## 权限判断

- 菜单、路由和按钮都消费 store 中的 permissions，并使用统一权限 code 判断。
- 权限 code 使用后端统一定义的三段式格式，例如 `system:user:list`。
- 菜单过滤只影响展示；路由守卫负责前端访问体验；后端权限中间件仍是最终安全边界。
- 按钮无权限时通常不展示；直接访问无权限路由时显示统一无权限结果或跳转到可访问页面。
- 不因角色名在前端硬编码全部权限，也不为 `super_admin` 增加前端绕过逻辑；以后端当前用户接口返回的 permissions 为准。
- 权限数据尚未恢复完成时，不应短暂渲染受保护页面或操作按钮。

## 更新流程

- 登录、刷新当前用户、分配角色或权限变化后，统一更新同一份 Zustand 状态。
- 当前用户信息请求失败时，根据统一 Response 决定保留错误状态或清理失效登录态，不在业务组件内处理底层 Axios 异常。
- 页面只通过公共 selector、hook 或判断函数消费认证状态，避免订阅无关字段造成重复渲染。

## 安全边界

- 前端权限只用于菜单、路由和按钮体验，所有重要接口必须由后端鉴权。
- 不把密码、JWT、Secret 或敏感用户信息输出到日志、错误提示或提交文件。
- 不以本地持久化内容作为可信授权依据；刷新后以服务端返回的当前用户信息为准。
