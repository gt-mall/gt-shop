# 02 微信收货地址导入完善

## 已有代码与缺口

- `miniapp/src/pages/address/index.vue` 已有微信端按钮和 `handleImportWechatAddress`，调用 `uni.chooseAddress` 后直接 `addAddress` 保存。
- `utils/addressParse.ts` 的 `resolveRegionCodes` 只匹配省份，市区使用省份前缀拼 `0100` / `0101`；未匹配省份甚至默认北京。微信导入、地址编辑/粘贴均有相关调用，不能把该结果当真实行政区划。
- `src/api/common.ts` 的 `getRegions()`、`/api/miniapp/regions` 已提供真实区划树；编辑页已加载它，后端 `internal/region/service.go` 的 `ValidateAndResolveAddress` 验证代码、名称和父子关系。
- 当前导入会打印整份姓名、电话、地址；缺操作锁、去重提示和选择模式下自动回填。
- `manifest.json` 的 `mp-weixin` 对象当前存在重复 `appid` 键，正式配置需要明确唯一值；不得在文档或日志复制 Secret。

## 执行提示词

先读取 README 公共约束。以修复既有导入能力为目标，复用地址创建接口，不新建微信地址专表。

1. 把导入流程提取为 `useWechatAddressImport` 或小型业务服务，由地址列表、地址编辑页和结算页入口复用。微信端展示按钮；H5 保留普通手动录入，不能出现可点击却永远无法工作的微信入口。
2. 点击后校验登录并设操作锁，调用原生选择；主动取消正常结束，权限拒绝、隐私未同意、平台不支持、网络失败分别给出可操作提示。授权恢复仅由用户操作触发，禁止循环弹授权或自动打开设置。
3. 移除原生响应的完整日志。姓名/手机/详细地址只在当前草稿中保留；不放 URL、不跨账号缓存、不打印。
4. 取得原生地址后先进入现有编辑表单预填，让用户确认保存。用 EventChannel/会话内草稿传递，离开后清理；识别从结算选择模式进入的来源。
5. 根据真实区划树按省 → 市 → 区逐级匹配，处理直辖市“北京市/市辖区”、合法省份简称及重名区县。名称有歧义或查无区划时保持未选状态，要求手动选择；禁止猜测代码。不要把微信 `nationalCode` 未经验证当 district_code。
6. 将 `resolveRegionCodes` 的虚构回退替换为“明确匹配或失败”的结果，并逐一改好编辑页、原生 picker、粘贴解析等调用方。后端 DTO 目前要求三个 code 必填，不可直接传空请求碰运气，也不要削弱后端验证。
7. 正确处理 `detailInfo` / 平台新字段的兼容，街道与详细地址避免重复拼接；手机号规范化后按现有后端规则验证，不自行截掉非法内容。以官方当前字段语义为准。
8. 保存前用规范化姓名、手机号、省市区 code、详细地址和当前账号已有地址比较；完全相同则提示复用已有地址，不重复插入。该方案只承诺单客户端防重；不新增全局地址唯一约束误伤合法业务。
9. 保存中防重复点击；失败保留草稿并恢复按钮。默认地址规则以后端为准，不能覆盖用户原默认地址。账号变化或原生选择晚返回时丢弃旧会话结果。
10. 来自结算时，保存/复用成功后沿现有 `selectAddress` 与返回链路带回实际 AddressResponse，让结算重新预览运费；普通地址管理进入则刷新列表。监听器及时移除，不能回填两次。
11. 整理 manifest 重复 AppID；保持有效环境配置，明确开发者平台合法域名、隐私声明及基础库要求。具体微信权限声明按执行时官方文档核实，不照搬其他平台字段。

## 验收

- 深圳南山区、杭州西湖区、北京海淀区、省直辖地区、同名区县、旧区划无法匹配各有真实区划树测试。
- 导入取消不创建地址；拒绝授权能继续手动录入；重复地址不重复保存；失败草稿保留。
- 结算中导入后正确更新收件人/运费，原默认地址不被意外替换。
- 双击、保存超时、账号切换、页面卸载不会重复保存或串号。
- 小程序源码测试与双端构建通过，补充开发者工具和真机验收记录。

官方资料：[uni.chooseAddress](https://uniapp.dcloud.net.cn/api/other/choose-address.html)。该能力不支持 H5；微信权限与隐私配置还需对照微信最新官方说明。
