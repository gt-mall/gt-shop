# 商城会员体系后续规划

## 1. 设计原则

- **核心与账户分离**：`member` 基础表仅保存会员核心身份、基础资料（昵称、头像、手机号、状态及登录时间），保持实体轻量与高内聚。
- **独立表与流水记账**：积分、余额等资金与资产账户型数据，在后续阶段采用独立的账户表配合增减变动流水表实现，满足精确核算与可追溯性要求。
- **不提前占位**：当前阶段不提前向 `member` 表添加 `points`、`balance`、`growth` 等字段，不创建空表或无实际业务逻辑的占位代码。
- **等级模型延迟绑定**：待会员等级业务实际落地时，再结合成长值计算规则综合决策 `level_id` / `growth` 的归属与存储形态。

## 2. 后续数据表规划

### 2.1 会员等级 (member_level)
- 规划用于配置会员等级门槛与权益规则（如等级名称、升级门槛成长值、折扣权益、免邮权益等）。
- 等级与会员解耦，便于运营灵活调整等级体系与晋升规则。

### 2.2 会员积分 (member_points & member_points_log)
- `member_points`：记录每个会员的当前有效积分、累计获得积分等账户汇总数据。
- `member_points_log`：详细记录每笔积分变动流水，包含关联业务（签到、购物赠送、积分抵扣、系统调整等）、变动前后分值、操作人/系统标识。

### 2.3 会员余额 (member_balance & member_balance_log)
- `member_balance`：记录会员账户可用余额、冻结金额等，金额严格遵循 `DECIMAL` 存储，精确转换为整数分或十进制进行计算。
- `member_balance_log`：详细记录余额资金流动明细，包含交易类型（充值、消费、退款、后台调整）、关联订单号、变动金额与期初/期末余额。

## 3. H5 手机号+密码认证与后续能力

### 3.1 当前实现 (第一版)
- **表结构**：采用 `member_account` 表（`account_type='mobile'`，`account` 存手机号，`password_hash` 存 bcrypt 哈希），与 `member` 和 `member_auth` 分离。
- **JWT 体系复用**：复用既有会员 JWT（issuer = `mall-miniapp-member`），H5 登录/注册后签发的 Token 与微信小程序完全一致，无缝访问 `/api/miniapp/member/me` 及其他受保护接口。
- **账号与密码安全**：账号不存在与密码错误对外统一提示“手机号或密码错误”，杜绝账号遍历枚举风险；密码采用 bcrypt 加密存储。

### 3.2 暂不实现能力 (后续能力规划)
为了快速进行 H5 测试与最小化迭代，第一版暂不实现以下能力，统一归入后续演进：
- **短信验证码**：注册与登录阶段暂不发短信验证码，后续视业务风控需求接入第三方短信通道。
- **找回密码 / 重置密码**：后续配合短信或安全邮箱验证流程落地。
- **修改密码**：后续在会员个人中心安全设置中提供旧密码校验或验证码修改。
- **邮箱注册 / 登录**：`member_account` 已具备扩展 `account_type='email'` 的能力，后续按需开放。
- **第三方 H5 OAuth**：如微信公众号网页授权、支付宝网页登录等。
- **账号注销**：后续提供注销协议签署与资产清算校验流程。
- **刷新 Token (Refresh Token)**：当前由客户端重新获取凭证或登录，后续评估双 Token 机制。

### 3.3 账号合并原则 (重要)
- **禁止自动合并**：严禁仅因 `member.mobile` 相同就自动把微信会员（`member_auth`）与 H5 会员（`member_account`）进行静默合并。
- **显式绑定流程**：微信用户与手机号账号的合并/绑定必须由用户在已登录状态下主动发起，经短信验证码核验后，通过显式的绑定流程安全地将 `member_account` 或 `member_auth` 关联到同一 `member_id`，避免资产混淆与越权安全事故。
